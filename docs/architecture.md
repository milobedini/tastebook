# Architecture

How Tastebook is built and run, and why. Decided in the engineering session on 2026-10-26; the rules agents follow are in [`AGENTS.md`](../AGENTS.md), and the product in the Linear team's Vision document. Items marked _planned_ are decided but not built yet; the Linear issue that builds them is named.

## Stack

| Part | Choice | Why |
| --- | --- | --- |
| Frontend | React single-page app with Vite, TanStack Query, react-router | Suits an app-like, phone-first product (cooking mode, a live shopping list); already built and working. |
| API | Django with Django REST framework, OpenAPI schema generated by drf-spectacular | Django's admin is the moderation and data-fixing tool; the generated contract keeps the two apps in step. |
| Database | Postgres | Already in use; Neon in the cloud. |
| Styling | Tailwind CSS with shadcn/ui (components copied into the repo, built on Radix) | Tastebook owns every component, Radix brings accessibility, and agents know it well. The look is decided in the design system session. _planned_ |

## Where it runs

Everything on Vercel. _planned: TAS-24._

| Part | How | Why |
| --- | --- | --- |
| Frontend | Static files | Nothing to run; fast from the edge. |
| API | Django as a Python function under `/api`, on the same domain as the frontend | One platform, same-origin cookies for sign-in, no CORS. Cold starts after idle time are acceptable at this scale. |
| Database | Neon Postgres, installed through the Vercel Marketplace | Free plan covers a household app; a database branch per preview. |
| Photos | Vercel Blob | Native, no extra account. |
| Domain | `tastebook.vercel.app` (or the nearest free name) until a custom domain is added | A domain can be added later without code changes. |

## Environments

| Environment | Database | Deployed when |
| --- | --- | --- |
| Local | Postgres in Docker (`compose.yaml`) | `pnpm dev` |
| Preview | Its own Neon branch | Every push to a PR |
| Production | Neon's main branch | Every merge to `main` |

Each build runs Django's migrations, then loads the catalogue from the repo (a no-op when nothing changed), so every deployment's schema matches its code and the catalogue changes through PRs like code. _planned: TAS-24._

## Accounts

_planned: Accounts and households._

- **Sign-in:** `django-allauth`, with a code sent by email or Google; no passwords. Nobody forgets a password they never set, Google covers most people, and accounts stay in Tastebook's own database (households and private recipes depend on them) rather than with a third party.
- **Sessions:** cookies on the same domain as the API.
- **Email:** Resend through the Vercel Marketplace (free plan, about 3,000 a month). From Resend's shared address until there's a custom domain.
- **Previews:** email codes only; Google can't redirect to preview addresses that change per PR. How end-to-end tests sign in on previews is decided in the Accounts and households PRD.
- **Staff:** the Django admin is for staff accounts only, and staff need two-factor sign-in with an authenticator app (allauth's MFA), because the admin can change every recipe and account.
- **Deleting an account** (UK GDPR's right to erasure): the account's private recipes are deleted; its public recipes stay, credited to "a former member", so saved links keep working.

## Photos

_planned: Real recipes._

- Resized in the browser before upload (longest side 1,600 px), stored in Vercel Blob.
- Every photo has an unguessable address. A private recipe's photo is only reachable by someone who has its address; there's no access check per image, which would need a server in front of every request.

## On the phone

- Light and dark follow the phone's setting, with a toggle to override it.
- Installable to the home screen. Recipes you've opened and the week's planned recipes are kept for reading offline, cooking mode included. Nothing can be edited offline: syncing offline changes is a project of its own.
- The shopping list polls every few seconds while it's open (TanStack Query's refetch interval), not WebSockets: simple and reliable on serverless, and a second's delay doesn't matter in a shop.

## Running it

| Need | How | Why |
| --- | --- | --- |
| Errors | Sentry for the frontend and Django, free plan, through the Marketplace. _planned: TAS-25._ | Problems are found without someone reporting them. |
| Success measures | Events in Tastebook's own database (a plan used, cooking mode opened, an import saved without fixes), shown on a staff page. _planned._ | Measures exactly what the Vision asks, sends nobody's data elsewhere, costs nothing. |
| Backups | A nightly GitHub Action dumps production into a private Blob store, kept 30 days. _planned: TAS-27._ | Neon's free plan only restores a few hours back, and losing the household's recipes is the worst thing that could happen. |
| Checks on previews | Playwright end to end, axe for WCAG 2.2 AA, Lighthouse on mobile. _planned: TAS-26._ | Work is checked as it ships, before review. Thresholds are in `AGENTS.md`, Standards. |
| Dependencies | Dependabot weekly with a 7-day cooldown; pnpm and uv ignore releases under a day old. | Routine updates without supply-chain surprises. |

## Code

- Organised by domain area, the same on both sides; see `AGENTS.md`, Domain areas, and [`GLOSSARY.md`](../GLOSSARY.md). A domain-driven layout keeps each area's language and rules together, and one issue mostly touches one area.
- Abstract on the third use, not before.
- Black-box tests only: the API, rendered pages, an area's public functions, Playwright on previews. Tests that survive refactoring are the ones worth having.
- Review is adversarial, against published standards (WCAG 2.2 AA, OWASP ASVS 5.0 Level 1 and the Top 10, Core Web Vitals, UK GDPR), and each fix proposes a guard against its whole class of problem.

## No AI inside the app

Tastebook makes no paid AI calls and can't run on a personal Claude subscription. Imports use the recipe data sites publish, rules for pasted text, or a person's own Claude with the Tastebook format. The factory that builds Tastebook does use Claude, on its owner's subscription.
