# Architecture

How Tastebook is built and run, and why. Decided in the engineering session on 2026-10-26; the rules agents follow are in [`AGENTS.md`](../AGENTS.md), and the product in the Linear team's Vision document. Items marked _planned_ are decided but not built yet; the Linear issue that builds them is named.

## Stack

| Part | Choice | Why |
| --- | --- | --- |
| Frontend | React single-page app with Vite, TanStack Query, react-router | Suits an app-like, phone-first product (cooking mode, a live shopping list); already built and working. |
| API | Django with Django REST framework, OpenAPI schema generated by drf-spectacular | Django's admin is the moderation and data-fixing tool; the generated contract keeps the two apps in step. |
| Database | Postgres | Already in use; Neon in the cloud. |
| Styling | Tailwind CSS with shadcn/ui (components copied into the repo, built on Radix) | Tastebook owns every component, Radix brings accessibility, and agents know it well. The look is decided in the design system session. _planned_ |

## Where it runs

Everything on Vercel, in one project with two [services](https://vercel.com/docs/services) (`vercel.json`): `frontend` and `backend` build separately and deploy together, so a preview's two halves always match. `/api/*` reaches Django; everything else gets the frontend. Functions run in London (`lhr1`), next to the database.

| Part | How | Why |
| --- | --- | --- |
| Frontend | Static files | Nothing to run; fast from the edge. |
| API | Django as a Python function under `/api`, on the same domain as the frontend | One platform, same-origin cookies for sign-in, no CORS. Cold starts after idle time are acceptable at this scale. |
| Database | Neon Postgres, through the Neon-managed integration from the Vercel Marketplace | Free plan covers a household app; a database branch per preview. Neon-managed rather than Vercel-managed because it deletes a preview's branch once its Git branch is gone (merged branches are deleted), which keeps within the free plan's 10 branches. One of the 10 is `previews-base`, the permanent empty branch previews are made from. |
| Photos | Vercel Blob | Native, no extra account. |
| Domain | <https://tastebook.dev>, registered through Vercel; `www.tastebook.dev` and the old address, `tastebook-app.vercel.app`, redirect to it | Until October 2026 production was at `tastebook-app.vercel.app`, because `tastebook.vercel.app` was taken and Vercel's first pick was `tastebook-sooty.vercel.app`. `.dev` is HTTPS only (HSTS preload), so nothing may build an `http://` production address. |

## Environments

| Environment | Database | Deployed when |
| --- | --- | --- |
| Local | Postgres in Docker (`compose.yaml`) | `pnpm dev` |
| Preview | Its own Neon branch, made from `previews-base`, which is empty and the Neon project's default branch | Every push to a PR |
| Production | Neon's main branch | Every merge to `main` |

Each build runs Django's migrations against its own database (`backend/build.py`, over Neon's direct connection; requests use the pooled one), so every deployment's schema matches its code. It then loads the catalogue from `backend/recipes/catalogue.json` with `manage.py load_catalogue`, which makes the database's recipes, ingredients and equipment what the file says, so the catalogue changes through PRs like code. The admin shows recipes, ingredients and equipment read-only, with a notice saying so, because the next deploy's load would undo an edit made there; cuisines aren't in the file, so they stay editable. A file the database can't hold fails the build. Every recipe is in the catalogue until households have private recipes, so the load removes any recipe the file doesn't list; private recipes will need a mark that keeps the load away from them.

- **Preview databases:** a preview's Neon branch is made from `previews-base`, an empty branch, so no account, household or private recipe from production ever reaches a preview. The build then migrates it and loads the catalogue, so a new preview opens with the catalogue and no accounts. As a backstop, a preview's build marks a database it finds empty (a comment on its `public` schema, which production's never has), and fails if an unmarked database holds any account after migrating (`backend/build.py`): households and private recipes belong to accounts, so a database without accounts holds neither, and a marked one holds only accounts made on that preview. Setting it up is a person's step, done once in Neon and not something the repo can do:
  1. In the Neon console, make a branch named `previews-base` from `main` with **Schema only**, so it copies no rows, then empty it in its SQL Editor with `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`. It has to be empty, not only rowless: with no rows in `django_migrations`, the build's `migrate` would try to make tables that already exist. Never make it, or reset it, from production's data.
  2. The integration has no setting for the branch previews are made from: it always makes them from the Neon project's default branch. So, in this order, first pin production in Neon console › Integrations › Vercel › Manage › Branches: set **Production branch** to `main` explicitly and save. Then make `previews-base` the default branch (Branches › `previews-base` › Set as default). Redeploy production in Vercel and check it still uses `main`. The other order would leave production following the default branch onto `previews-base`'s empty database.
  3. Delete any preview branch made before the change (named `preview/<git branch>` in Neon): the integration reuses a Git branch's database branch, so the next push to that PR makes a new one from `previews-base`.

  A preview whose build fails with "This preview's database holds accounts" was made from production's branch: check step 2, then delete that preview's branch and push again.

- **Hosts:** Django trusts the hosts Vercel gives the deployment (`VERCEL_URL`, `VERCEL_BRANCH_URL`, `VERCEL_PROJECT_PRODUCTION_URL`) and nothing else under `vercel.app`, both as allowed hosts and as CSRF trusted origins (`backend/config/settings.py`). Production's domain is trusted through `VERCEL_PROJECT_PRODUCTION_URL`, which Vercel sets to the project's production domain, so it needs no code change. Vercel only sets it on deployments made after the domain is added, though: when production's domain is added or changed, redeploy production before the API answers on it, and don't redirect the old address to the new one until then (in October 2026 the API answered 400 on `tastebook.dev` until a redeploy). `DJANGO_ALLOWED_HOSTS` adds allowed hosts but not CSRF trusted origins, so a domain listed only there would refuse sign-in and every other unsafe request.
- **Secrets:** `DJANGO_SECRET_KEY` is set per environment in Vercel, one value for production and another for previews. Neon sets `DATABASE_URL` and `DATABASE_URL_UNPOOLED`. `RESEND_API_KEY` sends sign-in emails, on production only (Accounts). Sentry sets `SENTRY_DSN`, plus `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT` for uploading source maps; none are set locally or in CI, so Sentry stays off there. The frontend's build passes the DSN, environment and commit to the browser by name (`frontend/vite.config.ts`), because Vite only exposes `VITE_*` variables.
- **Previews** are behind Vercel's sign-in (Deployment Protection). The checks on previews (TAS-26) get a bypass secret for automation. The Vercel toolbar, Comments included, is off for previews (project Settings › General › Vercel Toolbar), because Lighthouse would score its injected scripts, and in October 2026 its feedback script started setting a third-party cookie that failed Best Practices.
- **GitHub Actions secrets:** the checks on previews run from the deployed commit's own workflow file, a fork's PR included, so any repository secret is open to whoever opens a PR. The only one there is `VERCEL_AUTOMATION_BYPASS_SECRET`, which gets past previews' sign-in and nothing else. The factory's secrets (`CLAUDE_CODE_OAUTH_TOKEN`, `FACTORY_APP_CLIENT_ID`, `FACTORY_APP_PRIVATE_KEY`) are in the `factory` environment, whose deployments are limited to `main`; the factory's stage runs come from `repository_dispatch`, which runs on `main`.
- **The admin** isn't reachable on Vercel yet: only `/api` reaches Django until staff sign in with two factors (Accounts and households).

## Accounts

- **Sign-in:** `django-allauth`'s headless API under `/api/_allauth/` (the browser client: session cookies and CSRF), with a 6-digit code sent by email that works once, for 10 minutes; no passwords. Asking for a code for an address with no account answers `unknown_email`, and the client then signs up with it, which emails a code too. Signing in with Google is _planned: TAS-105_. Nobody forgets a password they never set, Google covers most people, and accounts stay in Tastebook's own database (households and private recipes depend on them) rather than with a third party. The account is `households.User`, with the email address as its identifier.
- **Sessions:** Django's database sessions, in cookies on the same domain as the API. A session lasts 30 days from its last request: every request sets the cookie again.
- **Email:** Resend over SMTP from `noreply@tastebook.dev` (`DJANGO_DEFAULT_FROM_EMAIL`), production only; `RESEND_API_KEY` is a Production secret and production won't start without it. Previews send no email; locally and in CI it goes to the console.
- **Previews:** email codes only; Google can't redirect to preview addresses that change per PR. Since previews send no email, only test accounts sign in there: addresses at `tastebook.test` (reserved by RFC 2606, so nobody can own one), whose codes the backend stores instead of sending. End-to-end tests read them from `GET /api/test-accounts/code/?email=`, which on previews needs the previews' bypass secret in `X-Test-Account-Secret`. Locally and in CI it needs nothing; on production it answers 404 and signing up refuses a `tastebook.test` address.
- **Staff:** the Django admin is for staff accounts only, and staff need two-factor sign-in with an authenticator app (allauth's MFA), because the admin can change every recipe and account.
- **Deleting an account** (UK GDPR's right to erasure): the account's private recipes are deleted; its public recipes stay, credited to "a former member", so saved links keep working.

## Photos

- Until uploads arrive, a photo is an image on Wikimedia Commons: the recipe stores its address and credit, and pages load Commons' thumbnails straight from `upload.wikimedia.org`.

Uploads are _planned: Accounts and households._

- Resized in the browser before upload (longest side 1,600 px), stored in Vercel Blob.
- Every photo has an unguessable address. A private recipe's photo is only reachable by someone who has its address; there's no access check per image, which would need a server in front of every request.

## On the phone

- Dark only (`docs/design.md`, Colour): one theme, no toggle.
- Installable to the home screen. Recipes you've opened and the week's planned recipes are kept for reading offline, cooking mode included. Nothing can be edited offline: syncing offline changes is a project of its own.
- The shopping list polls every few seconds while it's open (TanStack Query's refetch interval), not WebSockets: simple and reliable on serverless, and a second's delay doesn't matter in a shop.

## Running it

| Need | How | Why |
| --- | --- | --- |
| Errors | Sentry for the frontend and Django, free plan, through the Marketplace. Each error is tagged with its environment (`VERCEL_ENV`) and commit (`VERCEL_GIT_COMMIT_SHA`); no request bodies, cookies, user details or local variables are sent. The frontend's source maps are uploaded at build time and not deployed. Only production's browser reports errors, since a preview's sign-in redirects the tunnel's request; previews' server errors still reach Sentry. The browser sends its errors to `/monitoring` on Tastebook's own address (Sentry's `tunnel` option), and a rewrite in `vercel.json` forwards them to this Sentry project's ingest URL, fixed there so the path can't reach any other project; a new DSN means updating that rewrite. | Problems are found without someone reporting them. Ad and tracker blockers drop requests to `sentry.io`, but not to the site's own address. |
| Success measures | Events in Tastebook's own database (a plan used, cooking mode opened, an import saved without fixes), shown on a staff page. _planned._ | Measures exactly what the Vision asks, sends nobody's data elsewhere, costs nothing. |
| Backups | A nightly GitHub Action dumps production into a private Blob store, kept 30 days; see [Backups](#backups). | Neon's free plan only restores a few hours back, and losing the household's recipes is the worst thing that could happen. |
| Checks on previews | Playwright end to end, axe for WCAG 2.2 AA, Lighthouse on mobile, run by `.github/workflows/preview-checks.yml` when Vercel reports a preview deployed; results are a comment on the PR. | Work is checked as it ships, before review. Thresholds are in `AGENTS.md`, Standards. |
| Dependencies | Dependabot weekly with a 7-day cooldown; pnpm and uv ignore releases under a day old. | Routine updates without supply-chain surprises. |

## Backups

`.github/workflows/backup.yml` runs at 02:17 UTC every night (and on demand from the Actions tab). It dumps production with `pg_dump` 18 over Neon's direct connection, checks the dump holds table data, uploads it to the private Blob store `tastebook-backups` as `tastebook-<time taken>.dump`, then deletes dumps older than 30 days. The code is in `tools/backup/`.

- **Secrets:** the workflow reads `PRODUCTION_DATABASE_URL` (direct, unpooled) and `BACKUP_BLOB_READ_WRITE_TOKEN` from the GitHub environment `backups`, not the repository's secrets. Only `main` can deploy to that environment, so a workflow on any other branch can't read them. The store isn't connected to the Vercel project, so the app's own token can't read or delete backups; photos are in a different store.
- **A failed night:** the run fails and shows red in Actions, GitHub emails whoever last changed the workflow's schedule, and nothing is deleted, because pruning only follows a successful upload.
- **Keeping it running:** GitHub turns scheduled workflows off after 60 days without activity in the repo. If that happens, turn it back on from the workflow's page in Actions.

To restore, with the Postgres 18 client tools (`pg_restore`) on your `PATH`, from the repo root after `pnpm install`:

```sh
BACKUP_BLOB_READ_WRITE_TOKEN=<token> TARGET_DATABASE_URL=<direct connection string> pnpm --filter @tastebook/backup restore [tastebook-2026-10-26T021705Z.dump]
```

Leave out the dump's name to restore the latest. It drops and recreates the dump's tables in the target in one transaction, so a failed restore changes nothing.

- **Client tools on a Mac:** `brew install libpq` gives Postgres 18's `pg_restore`; it isn't linked, so put `/opt/homebrew/opt/libpq/bin` first on the `PATH` for the command.
- **The token:** Vercel → Storage → `tastebook-backups` → `.env.local`; paste the value alone, without its name or quotes.
- **The target:** a Neon branch's direct connection string (Neon console → Connect, with connection pooling off): it starts `postgresql://` and its host has no `-pooler`. Check the host is the branch you mean before running, never production's unless production is what you're recovering. Reading both values with `read -s` keeps them out of your shell history.
- **Trying it:** a restore into a copy of production looks the same whether it worked or not, so make a throwaway branch from production, change some rows on it, restore, compare it with production, then delete the branch. Tried this way on 26 Oct with the first backup: the changed rows, tables, constraints, indexes and sequences all matched production.

## Code

- Organised by domain area, the same on both sides; see `AGENTS.md`, Domain areas, and [`GLOSSARY.md`](../GLOSSARY.md). A domain-driven layout keeps each area's language and rules together, and one issue mostly touches one area.
- Abstract on the third use, not before.
- Black-box tests only: the API, rendered pages, an area's public functions, Playwright on previews. Tests that survive refactoring are the ones worth having.
- Review is adversarial, against published standards (WCAG 2.2 AA, OWASP ASVS 5.0 Level 1 and the Top 10, Core Web Vitals, UK GDPR), and each fix proposes a guard against its whole class of problem.

## No AI inside the app

Tastebook makes no paid AI calls and can't run on a personal Claude subscription. Imports use the recipe data sites publish, rules for pasted text, or a person's own Claude with the Tastebook format. The factory that builds Tastebook does use Claude, on its owner's subscription.
