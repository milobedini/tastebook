# Add an account page with your name and units

Linear: TAS-106

## Summary

A signed-in person gets an account page at `/account`, opened from the account menu, where they change the name shown on recipes they write and choose metric or US customary units. The unit choice is saved on the account, and every recipe page opens in it; signed out, recipe pages open in metric as today. It comes now because the account page is where TAS-133 (download everything) and TAS-134 (delete your account) will live, and it closes PRD requirements 6 ("You can change it later") and 8.

Evidence: feature. A new page, a new menu item, and recipe pages that open in US customary for an account that chose it.
Design: needed. The account page is a new screen and no board in `docs/design/` draws it. The menu's "Account" item is already drawn (`docs/design/dino/menu.dc.html`, `account-menu-open.dc.html`) and needs no design.
Components: none new or changed expected. The page is built from Page, Field, Input, Button, SegmentedControl, Loading, ErrorWithRetry and toasts; the design stage says so if it needs more.

## Product behaviour

1. You can change the name shown on recipes you write, from your account page.
2. Your unit choice is saved on your account and every recipe page opens in it; signed out, every recipe page opens in metric.

What else holds, each proved by a test below:

- The account menu has an "Account" item that opens the account page.
- Choosing units on the account page saves at once and says "Units saved"; if saving fails, the page says so and shows the units chosen before.
- Switching units on a recipe page changes that visit only; the saved choice stays as it was.
- Changing your name leaves your household's name as it is.
- Signed out, the account page sends you to sign in, then brings you back to it.

## Technical design

### How it works today

- `households.User` (`backend/households/models.py:35-58`) has `email`, `name`, `household` and no unit choice. The newest migration is `households/migrations/0003_sign_in_limits_cache.py`.
- `GET /api/account/` answers `{"account": {"email", "name"}}` or `{"account": null}`. `PATCH /api/account/` takes `{"name"}` only (`AccountNameSerializer`, `serializers.py:15-16`), calls `name_account` and answers the `Account`. Its schema body is `PatchedAccountName`.
- `name_account` (`services.py:32-41`) creates a household only when the account has none, so a second name already keeps the household's name (`test_saving_a_name_again_keeps_the_household_and_its_name`, `backend/tests/test_accounts.py:425`).
- The recipe page keeps its unit system in `useState<UnitSystem>('metric')` (`recipe-page.tsx:91`); `UnitSystem` is a hand-written `'metric' | 'us'` (`convert.ts:9`). The account menu has one item, "Sign out" (`app-layout.tsx:24-31`). No route needs a signed-in account yet.

### Approach, layer by layer

```mermaid
sequenceDiagram
    participant A as /account
    participant M as useChooseUnitSystem
    participant API as PATCH /api/account/
    participant C as Session cache
    participant R as /recipes/:slug
    A->>M: mutate("us"); control shows "us" while pending
    M->>API: {"unit_system": "us"}
    API-->>M: 200 {"email", "name", "unit_system": "us"}
    M->>C: setQueryData(SESSION_KEY, account)
    M-->>A: toast "Units saved"
    R->>C: useSession() → account.unit_system "us"
    R-->>R: RecipeBody opens in US customary; its switch overrides for this visit only
```

#### Model (`backend/households/models.py`)

```py
class UnitSystem(models.TextChoices):
    METRIC = 'metric', 'Metric'
    US = 'us', 'US customary'


class User(AbstractBaseUser, PermissionsMixin):
    ...
    # Every recipe page opens in it; the switch on a recipe page doesn't change it.
    unit_system = models.CharField(max_length=6, choices=UnitSystem.choices, default=UnitSystem.METRIC)
```

`UnitSystem` sits above `Household`. The values `metric` and `us` are the frontend's existing ones, so `convert.ts` keeps working unchanged once its type comes from the schema. Migration `0004_user_unit_system.py` adds the column; existing accounts get `metric`.

#### Service (`backend/households/services.py`)

```py
def update_account(user: User, name: str | None = None, unit_system: UnitSystem | None = None) -> User:
    """Saves whichever of the name and unit system are given, together; naming follows name_account."""
    with transaction.atomic():
        account = name_account(user, name) if name is not None else User.objects.select_for_update().get(pk=user.pk)
        if unit_system is not None:
            account.unit_system = unit_system
            account.save(update_fields=['unit_system'])
    return account
```

`name_account` stays as it is (the Google adapter calls it, `adapter.py:51`); its `transaction.atomic()` nests as a savepoint.

#### API contract

`backend/households/serializers.py`:

```py
class AccountSerializer(serializers.Serializer):
    email = serializers.EmailField()
    name = serializers.CharField()
    unit_system = serializers.ChoiceField(choices=UnitSystem.choices)


class AccountChangesSerializer(serializers.Serializer):
    name = serializers.CharField(max_length=NAME_MAX_LENGTH, required=False)
    unit_system = serializers.ChoiceField(choices=UnitSystem.choices, required=False)

    def validate(self, attrs: dict[str, Any]) -> dict[str, Any]:
        if not attrs:
            raise serializers.ValidationError('Send a name or a unit system.')
        return attrs
```

`AccountNameSerializer` is renamed to `AccountChangesSerializer` (its only user is the view). `SPECTACULAR_SETTINGS['ENUM_NAME_OVERRIDES']` gains `'UnitSystem': 'households.models.UnitSystem'`, with the existing comment covering it.

```diff
 GET /api/account/  200
-{"account": {"email": "sam@example.com", "name": "Milo"} | null}
+{"account": {"email": "sam@example.com", "name": "Milo", "unit_system": "metric" | "us"} | null}

 PATCH /api/account/  (signed in, X-CSRFToken)
-body PatchedAccountName  {"name"?: string}
+body PatchedAccountChanges  {"name"?: string, "unit_system"?: "metric" | "us"}
 200 Account (as above)
-400 {"name": [...]}
+400 {"name": [...]} | {"unit_system": [...]} | {"non_field_errors": ["Send a name or a unit system."]}
 403 signed out or no CSRF header
```

Generated types: `components['schemas']['Account']` gains `unit_system: UnitSystem` (required, since a plain `Serializer` field is); `components['schemas']['UnitSystem']` is `'metric' | 'us'`. The view's `@extend_schema` takes `request=AccountChangesSerializer` and the description "Saves the signed-in account's name, unit system or both. An account with no household gets one called \"<name>'s household\"; a later name leaves the household's name as it is."

```ts
type UnitSystem = components['schemas']['UnitSystem'];

// Saves the account's unit system and puts the answer in the session, so recipe pages open in it at once. Saves
// share a scope, so they reach the server in the order they were chosen and the last choice is the one kept.
export const useChooseUnitSystem = () => {
  const queryClient = useQueryClient();
  return useMutation({
    scope: { id: 'households-unit-system' },
    mutationFn: async (unitSystem: UnitSystem): Promise<Account> => {
      const { data, response } = await api.PATCH('/api/account/', { body: { unit_system: unitSystem } });
      if (data === undefined) {
        throw new Error(`Saving the unit system failed with ${response.status}`);
      }
      return data;
    },
    onSuccess: (account) => queryClient.setQueryData<Account | null>(SESSION_KEY, account)
  });
};
```

## Decisions

- Units save the moment you pick them and the name has its own "Save name" button, because a unit choice is a single tap with nothing to confirm, while a name is typed and needs a clear moment to be checked. The control shows the latest choice while it saves and returns to the saved one with an error toast if it fails. Asked: how should the account page save your name and your units? → Units save when picked.
- The recipe page's switch changes that visit only and never saves, because the account page is then the one place the choice is set, and a quick look in US cups doesn't change every recipe. Asked: should switching units on a recipe page also change your saved choice? → No, just this visit.
- Changing your name leaves the household's name as it is, which `name_account` already does; renaming a household belongs to the household page. Asked: when you change your name, should your household's name change with it? → Keep the household's name.
- The recipe page waits for the session before showing a recipe, rather than opening in metric and switching, because a US account would otherwise see metric amounts flash on a direct load. The session is already asked for by the top bar, so the wait adds no request, and a session that can't be checked opens in metric rather than blocking the recipe (agent).
- The unit choice lives in `households` (`UnitSystem` on `User`), not `recipes`, because `households` depends on no other area. The frontend's `UnitSystem` becomes the generated type, so both sides share one list of values (agent).
- `PATCH /api/account/` widens to take either field, or both, rather than a second endpoint, because both are the account's own settings and one partial update is what PATCH means; an empty body is refused so a request always changes something (agent).
- Unit saves share a TanStack Query mutation scope, so two quick choices reach the server in order and the last one wins, without a lock or a disabled control (agent).
- The account page says "US customary" where the recipe page's compact switch says "US", because the account page has room for the glossary's full term and the recipe page's control row doesn't (agent).
- One PR, not split: most of the files are one-line fixture changes, and the backend change has nothing to show without the page (agent).
