# Add an account menu to Dino's top bar

Linear: TAS-101

## Summary

Dino's top bar (TAS-83) has the wordmark and search, and nothing about who is signed in. This adds the account end of it: signed in, an avatar showing the first letter of the account's name that opens a menu headed by the name, with the items the page passes in; signed out, a Sign in link in the avatar's place. It adds two Dino components, `Avatar` and `Menu`, and gives `TopBar` an optional `account` prop. Nothing can sign in until TAS-102 (sign in with an email code), so the live top bar doesn't change in this issue: `AppLayout` passes no account, and the stories show every state.

Evidence: chore — `AppLayout` passes no account, so nobody in production sees a change; the Avatar, Menu and TopBar stories and their baselines show each state.
Design: needed — `docs/design.md:228` (Still to settle) leaves the avatar, the menu and the app bar to be designed when a project needs them, and no Dino board draws them.
Components: Avatar (new), Menu (new), TopBar (changed: signed-in and signed-out ends)

## Product behaviour

1. Signed in, the top bar shows an avatar with the name's first letter that opens a menu headed by the name.
2. Signed out, the top bar shows a Sign in link where the avatar would be.
3. The menu opens, moves and closes by keyboard with visible focus, and the avatar is named "Account for <name>".
4. Stories show signed in, signed out and the open menu.

## Technical design

- **Approach:** frontend only, all in `frontend/src/dino/`. A new `Avatar` (`avatar.tsx`) draws the letter in a circle. A new `Menu` (`menu.tsx`) wraps Radix `DropdownMenu`: a trigger, an optional heading and a list of link or action items. `TopBar` gains an optional `account` prop and renders the signed-in or signed-out end from it. The approved design lands as a Dino board, `docs/design/dino/account.dc.html` and its PNG, and `docs/design.md` gains Avatar and Menu rows and a fuller Top bar line.
- **API contract:** no change. No session or "me" endpoint exists; TAS-102 adds one and passes `account` from `AppLayout`.
- **Blast radius:** `TopBar` is rendered by `AppLayout` (`frontend/src/app/app-layout.tsx:10`), on every page. `account` is optional and `AppLayout` doesn't pass it, so the bar keeps its two-column grid and renders exactly as today; the proof is that the `Dino/TopBar` Default and Is Search Open baselines don't change and `frontend/src/app/app-layout.test.tsx` passes untouched. `frontend/.storybook/preview.tsx`'s `afterEach` runs after every story; adding `[role="menuitem"]` to its selector changes nothing for existing stories, since none renders a menu item (`grep -rn menuitem frontend/src` finds none today). `boards.ts` is read by `frontend/visual/stories.spec.ts`, whose "every story title has a board image" test fails until `Dino/Avatar` and `Dino/Menu` name a board that exists.
- **Not changing:** `AppLayout`, the search, the wordmark, `IconButton` and `Button`.

### Avatar

```ts
// frontend/src/dino/avatar.tsx
type AvatarProps = { name: string };

// Decorative: whoever renders it names the control it sits in.
export const Avatar = ({ name }: AvatarProps) => { /* … */ };
```

- Renders `<span aria-hidden="true">` holding the first character of `name.trim()`, upper-cased with `toLocaleUpperCase()`. Take the character with `Array.from(name.trim())[0]`, so a letter outside the Basic Multilingual Plane isn't split in half.
- A name that is blank after trimming shows Lucide's `UserRound` icon (`aria-hidden`, `currentColor`) instead of a letter.
- Size, colours and type come from the approved design; it is one size, sized for the top bar.

### Menu

```ts
// frontend/src/dino/menu.tsx
import { DropdownMenu } from 'radix-ui';

export type MenuItem =
  | { kind: 'link'; label: string; to: string }
  | { kind: 'action'; label: string; onSelect: () => void };

type MenuProps = {
  trigger: ReactElement; // a button; Radix adds aria-haspopup and aria-expanded
  heading?: string;
  items: MenuItem[];
};

export const Menu = ({ trigger, heading, items }: MenuProps) => { /* … */ };
```

- Structure: `DropdownMenu.Root` (uncontrolled, modal by default), `DropdownMenu.Trigger asChild` round `trigger`, then `DropdownMenu.Portal` › `DropdownMenu.Content` with `align="end"`, a side offset and collision padding of 20 px (the phone gutter), and the 150 ms fade from `sheet.tsx`.
- `heading` renders as `DropdownMenu.Label` before the items: text, not focusable, not a menu item. A long heading wraps; it is never truncated.
- One unit per item kind, picked by `kind`:
  - `MenuLinkItem`: `<DropdownMenu.Item asChild><Link to={item.to}>{item.label}</Link></DropdownMenu.Item>` (react-router's `Link`). Radix closes the menu on select and the link navigates.
  - `MenuActionItem`: `<DropdownMenu.Item onSelect={item.onSelect}>{item.label}</DropdownMenu.Item>`.
- Items key on `label`, which is unique within a menu.
- Every item is at least 44 px tall (`min-h-11`). The hover fill keys on `data-highlighted:`; the focus ring keys on `focus-visible:`, so a keyboard user sees the 3 px Ink ring and a pointer user sees only the fill.
- Radix supplies the keyboard: Enter, Space and Down arrow open the menu and focus the first item; Up arrow opens it on the last; Up and Down move, Home and End jump, typing a letter jumps to the item starting with it; Escape and Tab close it; Escape and choosing an item put focus back on the trigger.

### TopBar

```ts
// frontend/src/dino/top-bar.tsx
import type { MenuItem } from '@/dino/menu';

export type TopBarAccount =
  | { status: 'signed-in'; name: string; menuItems: MenuItem[] }
  | { status: 'signed-out'; signInTo: string };

type TopBarProps = {
  searchLabel: string;
  searchValue: string;
  onSearchValueChange: (text: string) => void;
  // Undefined shows neither end, as today; TAS-102 also leaves it undefined while it checks who is signed in.
  account?: TopBarAccount;
};
```

- One unit per status, both private to `top-bar.tsx`:
  - `AccountMenu` (signed in): `<Menu trigger={<button type="button" aria-label={label} className="…"><Avatar name={name} /></button>} heading={heading} items={menuItems} />`. `label` is `` `Account for ${name.trim()}` ``, or `Account` when the name is blank. `heading` is `name.trim()`, or undefined when blank. The button is at least 44 × 44 px with the 3 px Ink focus ring, flush (docs/design.md, States › Focus).
  - `SignInLink` (signed out): `<Button variant="secondary" asChild><Link to={signInTo}>Sign in</Link></Button>`. Secondary, not primary: peach is for the page's own main action (Rules › Colour). If the approved design draws the ghost variant instead, use ghost; never primary.
- Grid: with `account` undefined, every class stays exactly as today. With an account, the inner row's columns become `grid-cols-[minmax(0,1fr)_auto_auto]`, the search's `col-span-2` becomes `col-span-3`, and the account end sits at `col-start-3 row-start-1` at every width. In the DOM it comes last, after `<search>`, so the tab order is wordmark, search, account on a laptop. On a phone the search button and the account end share row 1; the gap between them comes from the approved design, and without one it stays `gap-x-6`.
- `index.ts` exports `Avatar`, `Menu`, `type MenuItem` and `type TopBarAccount`.

### Rules the design must meet

These go to the design stage with the spec, and implement checks the drawing against them.

- Draw the top bar signed in and signed out at phone (320 and 390 px) and laptop widths, with the search button or field beside the account end; and the open menu at both widths.
- The avatar: one size, its button at least 44 px; the first letter of the name, and a fallback icon for an account with no name. It isn't peach, mint, butter or pink: those colours mean the main action, chosen, time and favourites (Rules › Colour). An avatar on Surface with Ink text, like an icon button, is the expected starting point.
- The avatar button's states: rest, hover, pressed (shrinks 92 to 94%, as small round controls), focus (3 px Ink ring, flush, never standing off the circle) and expanded while its menu is open.
- The menu: a panel on Surface, its corner per Space and shape (a panel's 24 px, its items the panel's corner less its border and padding), and no shadow unless the doc gains a rule for one (the lift is only for polaroids, the dock and sheets). The heading in a type role from the Type table, items in Label or Body, each at least 44 px tall, with hover, pressed and focus states.
- Sign in: an existing Button variant (secondary or ghost), never primary.
- A forced-colours drawing of the avatar, the open menu with a focused item, and Sign in.
- Motion: the menu fades in 150 ms or less, and not at all under `prefers-reduced-motion`.

## Decisions

- **The live top bar doesn't change until TAS-102**, because nothing can sign in yet and a Sign in link that leads nowhere would be a dead end in production. `account` is optional and `AppLayout` passes none. Asked: Should the live top bar change before sign-in exists? → No change until TAS-102.
- **The avatar shows the first letter of the name**, upper-cased, because it reads as the person at a glance and needs no photo. Asked: What should the avatar show? → First letter of the name.
- **The open menu is headed by the name**, not the email, because the name is what the household knows each other by and an email in a shared kitchen screen shows more than it needs to (UK GDPR, collect and show only what's needed). Asked: What should head the open menu? → The name.
- **The page passes the menu's items in**, as `{ kind, label, to | onSelect }`, because the items belong to the areas that own them (TAS-106's account page, TAS-102's sign out) and Dino stays free of routes and data. Asked: Should the top bar take its menu items from the page, or fix them in Dino? → Passed in by the page.
- **`account` is a union on `status`, and undefined shows neither end**, because there are three states, not two: signed in, signed out, and not known yet. Undefined keeps today's bar now and covers TAS-102's check of who is signed in, so the bar doesn't flash Sign in to someone who is signed in.
- **Two components, `Avatar` and `Menu`, from their first use**, because `docs/design.md` names both as part of the look (`AGENTS.md`, Dino component from its first use). `Menu` is generic (trigger, heading, items) rather than an account menu, so its next user needs no new component; the account wiring stays in `TopBar`.
- **Wrap Radix `DropdownMenu`** rather than build a menu, because `radix-ui` is a dependency, `Sheet` and `Checkbox` already wrap it, and it gives the WAI-ARIA menu button pattern (roles, arrow keys, typeahead, Escape, focus return) that criterion 3 asks for.
- **The avatar button is named "Account for <name>"**, because its visible text is one letter, and the name says whose account it is; Radix adds `aria-haspopup="menu"`, so screen readers announce it as a menu button. The name contains the visible letter (WCAG 2.5.3, Label in Name).
- **Sign in is a secondary Button link**, because the top bar is on every page and one peach button per screen belongs to the page's main action.
- **The 44 px check learns `[role="menuitem"]`**, because an action item is a `div` the check would miss, and menu items are targets like any other.
- **`docs/design.md` drops "app bar" from Still to settle**, because TAS-83 built it as the top bar and this issue settles its account end.
- **No icons beside menu items**, because neither criterion asks for them; a later design can add them.
