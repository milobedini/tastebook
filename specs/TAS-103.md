# Ask for your name on first sign-in, in a household of one

Linear: TAS-103

## Summary

Accounts made by TAS-102 have only an email address, so the top bar names everyone "Account" and nothing can be credited "by Milo". This asks every signed-in account with no name for one, on its own page, before it can use the rest of Tastebook, and saving it puts the account in a new household of one called "<name>'s household". Households come now because private recipes, lists and invites (TAS-108, TAS-114) all hang off them.

Evidence: feature. A new page every new account sees, and the top bar's avatar and menu now show the name.
Design: needed. The name page is a new screen and no board in `docs/design/` draws it. The top bar's named avatar and menu heading are already drawn (`docs/design/dino/account*.dc.html`) and need no design.
Components: none new or changed expected. The page is built from Page, Field, Input, Button, Banner, Loading and ErrorWithRetry; the design stage says so if it needs more.

## Product behaviour

1. A signed-in account with no name is sent to the name page from any page.
2. Saving a name puts a new account in a household called "<name>'s household".

What else holds, each proved by a test below:

- The name page asks for "Your name", says it shows on recipes you write, and won't take a blank one.
- After saving, you land on the page you were going to, and the top bar shows your initial and your name.
- An account that already has a name is never sent to the name page again.
- Signed out, every page works as today.

## Technical design

### How it works today

- `households.User` (`backend/households/models.py:24-38`) has `email`, `is_staff`, `is_active`, `date_joined`. No `Household` model exists. The one migration is `households/migrations/0001_initial.py`.
- `GET /api/account/` (`CurrentAccountView`, `backend/households/views.py:49-59`) answers `{"account": {"email": …}}` or `{"account": null}` and sets the CSRF cookie. No unsafe DRF endpoint exists yet: every typed request (`frontend/src/api/client.ts`) is a `GET`, and only allauth's own requests (`frontend/src/households/auth-api.ts`) send `X-CSRFToken`.
- `useSession()` (`frontend/src/households/session-api.ts:9-21`) returns `{ account, isPending, isError }`. `AppLayout` (`frontend/src/app/app-layout.tsx:20-34`) passes the top bar `name: ''`, so the avatar shows its icon and the button is named "Account".
- `useConfirmCode`'s `onSuccess` returns the session query's `invalidateQueries` promise, so `mutateAsync` resolves only once the session holds the new account; the sign-in page then navigates to `next` (`sign-in-page.tsx:221`).

### Approach, layer by layer

```mermaid
sequenceDiagram
    participant P as Any page
    participant G as NameGate (layout route)
    participant W as /welcome
    participant A as PATCH /api/account/
    participant S as name_account()
    P->>G: render, session says name ""
    G-->>W: Navigate replace to /welcome?next=<path+search>
    W->>A: {"name": "Milo"} with X-CSRFToken
    A->>S: name_account(user, "Milo")
    S->>S: lock the user row; set name; no household? create "Milo's household"
    A-->>W: 200 {"email": …, "name": "Milo"}
    W->>W: session cache := that account
    W-->>P: navigate replace to next
```

#### Models (`backend/households/models.py`)

```py
NAME_MAX_LENGTH = 50


class Household(models.Model):
    name = models.CharField(max_length=100)

    def __str__(self) -> str:
        return self.name


class User(AbstractBaseUser, PermissionsMixin):
    email = models.EmailField(unique=True)
    # Blank until the account gives it on the name page; shown on recipes it writes ("by Milo").
    name = models.CharField(max_length=NAME_MAX_LENGTH, blank=True)
    household = models.ForeignKey(Household, null=True, blank=True, on_delete=models.PROTECT, related_name='members')
    ...  # the existing fields, manager and constants unchanged

    class Meta:
        constraints = [
            # Every named account belongs to a household: the name and the household are saved together.
            models.CheckConstraint(
                condition=models.Q(name='') | models.Q(household__isnull=False),
                name='named_account_has_household',
            ),
        ]
```

- `Household` sits above `User` in the file. `Household.name` allows 100 characters, since TAS-108 lets members rename it.
- `on_delete=PROTECT`: a household with members can't be deleted. Deleting an empty household is requirement 20's, later.
- Migration `backend/households/migrations/0002_household_user_name_user_household.py` from `makemigrations households` (the implementer keeps whatever name `makemigrations` gives). Existing accounts get `name = ''` and no household; no data migration. They're asked on their next page load (Decisions).
- Django 6.1's `CheckConstraint` takes `condition=` (`check=` is gone).

#### Service (`backend/households/services.py`)

```py
def household_name_for(name: str) -> str:
    return f"{name}'s household"


def name_account(user: User, name: str) -> User:
    """Sets the account's name; an account with no household gets a new one, named after it."""
```

- `name_account` runs in `transaction.atomic()`. It reloads the user with `User.objects.select_for_update().get(pk=user.pk)`, so two saves at once can't make two households. It sets `name`; when `household_id` is `None` it creates `Household(name=household_name_for(name))` and sets it; then `save(update_fields=['name', 'household'])` and returns the reloaded user.
- A second call with a different name changes `name` only. The household keeps its name (requirement 11: members rename it, TAS-108).
- `name` arrives already trimmed and validated by the serializer.

#### Serializers (`backend/households/serializers.py`)

```py
class AccountSerializer(serializers.Serializer):
    email = serializers.EmailField()
    name = serializers.CharField()


class AccountNameSerializer(serializers.Serializer):
    name = serializers.CharField(max_length=NAME_MAX_LENGTH)
```

- Plain `Serializer`s, so `name` is required in the generated types (`name: string`), never optional.
- `CharField` trims whitespace and refuses blank by default: `"   "` is refused with DRF's "This field may not be blank.", `"  Milo "` saves as `"Milo"`. Over 50 characters: "Ensure this field has no more than 50 characters."

#### Endpoint (`backend/households/views.py`)

`CurrentAccountView` gains `patch`:

```py
@extend_schema(
    operation_id='current_account_partial_update',
    request=AccountNameSerializer,
    responses={200: AccountSerializer, 400: None, 403: None},
    description="Saves the signed-in account's name. An account with no household gets one called "
    '"<name>\'s household".',
)
def patch(self, request: Request) -> Response:
    if not request.user.is_authenticated:
        raise NotAuthenticated
    names = AccountNameSerializer(data=request.data)
    names.is_valid(raise_exception=True)
    account = name_account(request.user, names.validated_data['name'])
    return Response(AccountSerializer(account).data)
```

- Signed out: `403` (DRF's `NotAuthenticated` under session authentication has no `WWW-Authenticate`, so it answers `403`). A missing or wrong CSRF token: `403` from `SessionAuthentication`.
- `get` is unchanged; `AccountSerializer` now adds `name`, so it answers `{"account": {"email": "sam@example.com", "name": ""}}` before a name is saved.
- `ensure_csrf_cookie` stays on `get` only.

#### API contract

```diff
 GET  /api/account/   200 {"account": {"email": string, "name": string} | null}
+PATCH /api/account/  {"name": string (1–50, trimmed)} → 200 {"email": string, "name": string} | 400 | 403
```

`backend/schema.yml` and `frontend/src/api/schema.d.ts` are regenerated together (`AGENTS.md`, API contract). `components['schemas']['Account']` gains `name: string`; `AccountName` is new.

#### Typed client sends CSRF (`frontend/src/api/client.ts`)

The name save is the first unsafe request through the typed client, and Django's session authentication checks CSRF on it. Add one middleware:

```ts
const SAFE_METHODS = new Set(['GET', 'HEAD', 'OPTIONS']);

// Django checks CSRF on a signed-in account's unsafe requests; GET /api/account/ sets the cookie on every page.
api.use({
  onRequest: ({ request }) => {
    const token = csrfToken();
    if (!SAFE_METHODS.has(request.method) && token !== undefined) {
      request.headers.set('X-CSRFToken', token);
    }
    return request;
  }
});
```

`csrfToken()` is a module-level copy of the one in `auth-api.ts:29-33` (two uses; `AGENTS.md` abstracts on the third). `auth-api.ts` keeps its own.

- `frontend/src/households/name-api.ts` (new):

```ts
export type NameSave = { kind: 'saved'; account: Account } | { kind: 'refused'; message: string };

// Saves the name and puts the answer straight in the session, so the gate lets the person through at once.
export const useSaveName = () => {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (name: string): Promise<NameSave> => { … },
    onSuccess: (result) =>
      result.kind === 'saved' ? queryClient.setQueryData<Account | null>(SESSION_KEY, result.account) : undefined
  });
};
```

`mutationFn` calls `api.PATCH('/api/account/', { body: { name } })`. `200` → `saved` with the body. `400` → `refused` with the first message under `name` in the body, or "Enter your name, like Milo." when there is none. Anything else (`403`, `5xx`, a network failure) throws.

#### The gate (`frontend/src/households/name-gate.tsx`, new)

A pathless layout route inside `AppLayout`, around every page:

```tsx
export const WELCOME_PATH = '/welcome';
const SIGN_IN_PATH = '/sign-in';

// A signed-in account with no name gives one before anything else. The sign-in page sends you on to `next`
// itself, so the gate picks you up there, with the right `next`.
export const NameGate = () => {
  const { account } = useSession();
  const { pathname, search } = useLocation();
  if (account?.name === '' && pathname !== WELCOME_PATH && pathname !== SIGN_IN_PATH) {
    return <Navigate to={`${WELCOME_PATH}?next=${encodeURIComponent(pathname + search)}`} replace />;
  }
  return <Outlet />;
};
```

- While the session is pending or has failed, the page renders as today: blocking every visitor's page on the session request would cost every page's LCP, and signed out is the common case.
- `frontend/src/app/routes.tsx` (edit): `AppLayout`'s children become one `{ Component: NameGate, children: [...] }` holding today's routes plus `{ path: '/welcome', Component: WelcomePage }`, before `'*'`.

## Decisions

- **The name is required before using Tastebook**, because it shows on recipes and names the household, and a skippable name needs a stand-in for both and a way to ask again. Asked: must a new account give its name, or can it skip? → Required.
- **The name is asked on its own page, `/welcome`, that any page sends a nameless account to**, because it also catches accounts made before this ships and, later, Google sign-ins (TAS-105), which never pass the sign-in page. Asked: where should Tastebook ask for the name? → Own page, from any page.
- **The household is made when the name is saved, in one service**, so it has its real name from the start and only one place makes it; the database's `named_account_has_household` constraint guarantees every named account has one. An account has no household until then. Asked: when should an account's household of one be made? → When the name is saved.
- **Existing accounts get no data migration**: they're nameless, so the gate asks them on their next page load and their household is made then, the same path as a new account.
- **`PATCH /api/account/`, not a name-only endpoint**, because TAS-106 (changing your name and units) edits the same account and can grow this one. It already lets a named account change its name (no page offers it until TAS-106), and that never renames the household.
- **The account response carries `name` but not the household**, because no page shows the household until TAS-108, which adds what its page needs. The backend tests prove the household from the database.
- **The gate is a layout route that renders pages while the session loads**, because holding every page until the session answers would slow every signed-out visit; a nameless account sees the page briefly, then the name page.
- **The gate skips `/sign-in`**, because the sign-in page sends a new account on to `next` itself, and the gate then catches it there with the right `next`, rather than nesting `/sign-in?next=…` inside `/welcome?next=…`.
- **The typed client sends `X-CSRFToken` on every unsafe request**, because this is the first one and every later unsafe DRF endpoint needs the same; `csrfToken()` is copied, not shared, until a third use.
- **Saving puts the returned account straight into the session cache, then navigates**, so the gate never sees the stale nameless account and bounces back to `/welcome`.
- **`select_for_update` on the user while naming**, because two saves at once (a double press, two tabs) would otherwise make two households and orphan one.
